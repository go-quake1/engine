# The BSP world on the GPU, 2026-11-02

Step 3 of the GPU renderer plan: the world itself is drawn on the GPU
(package `render/gpuworld`, on go-gfx/webgpu), into the same 8-bit
palettized frame the software renderer writes, so that the presenter
displays it and the look stays the software one.

In scope: the BSP faces the PVS and the BSP walk select, their base textures,
and the lightmaps. Not yet: alias models, sky, water and lava, dynamic lights,
animated lightstyles (the lightmap is style 0). Sky and water faces are
skipped by both the GPU and the reference.

## Bibliography (what was opened)

- `reference/common/gl_rsurf.c` (the tyrquake mirror of GLQuake's surface
  code): `R_BuildLightMap` (line 115), the lightmap block upload (about 194 to
  260), `GL_BuildLightmaps` (about 2332 to 2387), `R_RecursiveWorldNode`
  (line 2090) and `R_DrawWorld` (line 2202). `gl_rmain.c`: only the call site
  of `R_DrawWorld` (line 1820).
- `reference/common/include/bspfile.h`: `LUMP_LIGHTING` (8), `texinfo_t`,
  `bsp29_dface_t` (`styles[4]`, `lightofs`: "start of [numstyles*surfsize]
  samples"), `MAXLIGHTMAPS` 4.
- The engine's own ports, which are the oracle: `bsprender` (`MarkVisibleLeaves`,
  `WalkWorld`, `FaceLightmapInfo`, `TransformFaceLightmapped`) and
  `render.FillPerspectiveLightmappedPolygon`, whose per-pixel algorithm the
  shader reproduces (wrap the texture coordinate, sample the lightmap
  bilinearly, colormap row `(255 - sample) >> 2`, colormap lookup).

What the sources say, and how it bears on the reference:

- `R_RecursiveWorldNode` skips solid nodes, nodes not in the PVS
  (`visframe != r_visframecount`) and nodes outside the frustum, walks the
  near child first, marks leaf surfaces, and then **culls back faces per
  surface** (`(dot < 0) ^ !!(surf->flags & SURF_PLANEBACK)`) and surfaces
  outside the frustum before chaining them for drawing. GLQuake then relies
  on the depth buffer. The engine's `bsprender.WalkWorld` returns the faces
  front to back but does **not** cull back faces (its own comment says that
  lives in the rasterizer), and `FillPerspectiveLightmappedPolygon` /
  `FillTexturedPolygon` have no depth test. So the software world, and the
  GPU world that matches it, draw far over near in walk order. Measured:
  drawing the same visible faces in the reverse order changes 19.2 % of the
  pixels of the 16 views. The picture is a plausible interior, not a correct
  Quake image where faces overlap. Matching it is the acceptance criterion
  of this step; hidden-surface handling (back-face cull plus a depth test or
  the right order) is a separate step. (Update, v0.9.0, #74: the reference and
  the GPU now draw the list in reverse, which is Quake's first-key-wins rule,
  `r_edge.c` `R_LeadingEdge`; see
  [2026-11-04-surfcache.md](2026-11-04-surfcache.md). The figures of this page
  were measured in the old order. Back faces are still not culled.)
- `R_BuildLightMap`: a surface's lightmap is `(extents >> 4) + 1` samples in
  each direction and style `n` is scaled by the lightstyle value; GL then
  shifts by 7 (or 8 with overbright), so GLQuake's static light is about
  twice the stored sample unless overbright is on (the scale is the lightstyle
  value, 8.8 fixed point; I did not open the lightstyle table). The software filler (and so the
  reference and the GPU) use the sample unscaled. `FaceLightmapInfo` computes
  the same extents.

## Design

- Per map, once: every drawn face is a triangle fan of vertices that carry the
  world position, the texture uv, the lightmap uv, and the face's rectangles
  in two atlases (base textures, 2048 x 320 texels for e1m1; lightmap planes,
  2048 x 207) and a 256 x 64 colormap texture, all `r8uint`.
- Per frame: `worldview.Visible` (PVS marking and BSP walk) gives the faces in
  the walk's order; one `Recorder` submit writes the 64-byte uniform (view
  transform, field of view) and issues one `DrawIndexed` per face into an
  `r8uint` target cleared to the sky-like index, with no depth test.
- The vertex shader reproduces the software projection (view-space depth
  clamped to the near plane, perspective-correct varyings from clip
  `w = depth`); the fragment shader reproduces
  `FillPerspectiveLightmappedPolygon` per pixel.
- The target is an index texture the presenter can bind directly (not wired in
  this step: the check reads it back).

## Acceptance: pixel diff against the software world

`cmd/quake-worldcheck` (browser test, needs the shareware `pak0.pak` through
`QUAKE_PAK`, skipped without it): 16 fixed e1m1 views (4 in-map origins times
4 yaws, `worldview.Views`) at 320 x 200, GPU world against
`worldview.DrawSoftware`, on the Apple GPU (adapter `apple metal-3`, not a
fallback; the test fails on a fallback adapter when `QUAKE_REQUIRE_GPU=1`).

| | |
|---|---|
| Faces on the GPU | 5149 (24,645 vertices, 14,347 triangles) |
| Pixels compared | 1,024,000 (16 frames) |
| **Identical palette index** | **94.9 %** (50,324 differ, 4.91 %) |
| **Unexplained** | **1.52 %** (15,522 pixels) |
| Worst view | 4.6 % unexplained (view 15); best 0 (view 5) |

*Unexplained* means: the pixel differs and the GPU's index is not the
reference's index at any of the 8 neighbouring pixels, i.e. it is not a
one-pixel shift of the same image. **Stated tolerance: 2.5 % unexplained over
the 16 views**; measured 1.52 %. Exact equality is not expected.

A planted negative proves the comparison can fail: with the GPU given a
colormap one eighth of the table too dark (every light level), 77.6 % of the
pixels are unexplained and the check fails (`TestDamagedColormapFails`).

### Where the two differ (attribution by removal)

Each probe removes one ingredient on **both** sides and reruns the same 16
views (`TestAttribution`, `QUAKE_ATTRIBUTION=1`):

| probe | differ | unexplained |
|---|---|---|
| nothing removed (the acceptance run) | 4.91 % | 1.52 % |
| every lightmap flat (light kept, texture kept) | 5.39 % | 2.01 % |
| every texture one flat colour (lightmaps kept) | 0.70 % | 0.04 % |
| flat light and flat texture | 0.01 % (111 pixels) | 0 |

Findings:

- **Coverage and overdraw agree**: with neither texture nor light, 111 of
  1,024,000 pixels differ and none is unexplained. So the polygon coverage
  rules (ties on edges), the sample positions and the overdraw order are not
  where the differences come from. (A first attempt to move the GPU polygons
  half a pixel to match the software scanline made 49 % of the pixels
  differ and was reverted: they already agree.)
- **Lighting is not it**: with textures flat and the lightmaps kept, only
  0.04 % are unexplained. float32 against float64 lightmap interpolation
  costs at most an occasional colormap row.
- **Texel selection is it**: with real textures 1.5 to 2 % are unexplained,
  with flat textures 0.04 %. The remaining difference is which texel of the
  texture a pixel takes. The consistent cause in the code
  (`render.PerspSubdivStep` = 8) is that the software filler is
  perspective-correct only at every 8th pixel and steps affinely between,
  while the GPU interpolates exactly, so on foreshortened surfaces the two
  disagree by a texel at texel boundaries. That cause is **not isolated**:
  there is no probe that changes the subdivision step; texel selection by
  `floor` of the interpolated coordinate at wrap seams is a second candidate.

## Cost at 1280 x 800

The workload is e1m1 from the fixed views, in Chrome for Testing 156 (wasm,
single thread), 7 browser runs, load 5.8 to 7.9 before and after each (5 runs
discarded above 8). In each run the three paths alternate frame by frame on
the 16 views, after a warm-up pass; medians of the per-frame times,
`median (min-max)` over the 7 runs. All three draw the same visible faces
(sky and water skipped).

| per frame | time |
|---|---|
| **Engine's software world path** (`worldview.DrawEngine`: affine `FillTexturedPolygon`, identity colormap, as `game.setupRenderer` runs it), wall | **9.58 ms** (9.33-9.85); p95 15.67 ms |
| Lightmapped software reference (`worldview.DrawSoftware`), wall | 75.55 ms (75.08-76.15); p95 138.15 ms |
| **GPU world**, CPU time (PVS walk, draw list, submit) | **0.170 ms** (0.165-0.180); p95 0.225 ms |
| **GPU world**, wall until the GPU is idle | **1.275 ms** (1.255-1.295); p95 1.405 ms |

The comparable pair is the engine's shipped path (unlit, affine) against the
GPU world's wall time: **9.58 ms against 1.28 ms, 7.5 times**, with the
caveat that the GPU draws the lightmapped, perspective-correct picture and
the engine's path draws an unlit one. The lightmapped reference is the
like-for-like picture and is 59 times the GPU's wall time.

- **GPU time itself is not measured.** The wall figure serialises the frame
  (submit, then wait for `onSubmittedWorkDone`), so it is the CPU time plus
  the GPU's execution plus the browser's completion latency. Timestamp
  queries need `QuerySet` and `timestampWrites`, which go-gfx/webgpu does
  not have yet (go-gfx/webgpu#16).
- **v0.2.1 cannot be measured on e1m1.** `game.loadBSP` opens
  `maps/start.bsp` first, so a session built on this pak renders `start`
  whatever map is asked, its benchmark cannot fetch a pak in the browser, and
  the load stayed above 8 for the one native run attempted. `worldview.DrawEngine`
  is the engine's world loop on e1m1 instead; it is not the engine's whole
  frame (no models, particles, sprites, HUD, 2D layers).
- No model, particle, sprite or HUD is drawn by any of the three.

## What remains

Hidden-surface handling that matches Quake (back-face cull and the right
order or a depth test, on both sides); sky and water; animated lightstyles
and dynamic lights; alias models; binding `Renderer.Target()` in the
presenter (an r8uint texture the presenter can read directly instead of the
CPU upload); GPU timestamps; PVS and the walk on the GPU (0.17 ms of CPU

## Update 2026-11-03: the texel selection is isolated and fixed (step 5)

The step 3 text above says the texel-selection cause was "not isolated" and
that "coverage and overdraw agree". Both statements were wrong or incomplete.

- Opened: `reference/common/d_scan.c` `D_DrawSpans8` (line 333): `count >= 8`,
  steps `(snext - s) >> 3`, the last span by division by `spancount - 1`.
  The engine's `render.FillPerspectiveLightmappedPolygon` already does exactly
  that (`PerspSubdivStep` 8); the GPU was perspective-exact per pixel.
- **Probe** (`--exactSpans`, `render.PerspSubdivStep = 1`, the reference made
  exact per pixel; `TestAttribution`): differing pixels 4.91 % to 1.79 %,
  unexplained 1.52 % to 0.56 %. So the 8-pixel steps are most of the step 3
  mismatch.
- **Coverage**: the reference takes a pixel by its left edge (`ceil(xLeft)`),
  the GPU by its centre. The "flat light, flat texture" probe cannot see that
  (every pixel has the same colour), so I had read it as agreement. The
  one-pixel-shift rule in the metric hid it.

The world shader now reproduces both: the polygon is moved half a pixel right,
and each fragment rebuilds the reference's span from the face's polygon
(a face table and a world-space vertex buffer): the scanline run from the
polygon's edges at the scanline centre, sub-spans of 8 pixels from the run's
first pixel, (1/z, u/z, v/z) from the edge crossings with depth clamped to the
near plane as `TransformFaceLightmapped` does, divided at the sub-span ends and
interpolated linearly between (the last span ends on the run's last pixel).
Same 16 views, same 2.5 % tolerance:

| | differ | unexplained |
|---|---|---|
| step 3 | 4.91 % (50,324) | 1.52 % (15,522) |
| **now** | **0.02 % (208)** | **0.006 % (63)** |
| now, light flat | 0.02 % | 0.01 % |
| now, texture flat | 0.00 % (10) | 0 |
| now, reference exact per pixel (the GPU still does 8) | 3.35 % | 0.99 % |

The planted negative still fails (77.64 %). What remains of the world's
mismatch is 208 pixels of 1,024,000.

Cost, 1280 x 800, 7 rounds, load 6.1 to 7.9 (7 runs discarded above 8), the
same harness as above: GPU world wall until idle **1.420 ms** (1.400-1.445),
against 1.275 ms in step 3: the per-fragment polygon walk costs about 0.15 ms.
Software lightmapped reference 76.2 ms; the engine's software world path
9.87 ms.
