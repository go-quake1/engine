# The BSP world on the GPU, 2026-11-02

Step 3 of the GPU renderer plan: the world itself is drawn on the GPU
(package `render/gpuworld`, on go-gfx/webgpu), into the same 8-bit
palettized frame the software renderer writes, so that the presenter
displays it and the look stays the software one.

In scope: the BSP faces the PVS and the BSP walk select, their base textures,
and the lightmaps. Not yet: alias models, sky, water and lava, dynamic lights,
animated lightstyles (the lightmap is style 0). Sky and water faces are
skipped by both the GPU and the reference.

## Bibliography (what was opened)

- `reference/common/gl_rsurf.c` (the tyrquake mirror of GLQuake's surface
  code): `R_BuildLightMap` (line 115), the lightmap block upload (about 194 to
  260) and `GL_BuildLightmaps` (about 2332 to 2387): lightmaps are packed in
  `BLOCK_WIDTH` blocks, which is what the lightmap atlas does here.
- The engine's own ports, which are the oracle: `bsprender` (`MarkVisibleLeaves`,
  `WalkWorld`, `FaceLightmapInfo`, `TransformFaceLightmapped`) and
  `render.FillPerspectiveLightmappedPolygon`, whose per-pixel algorithm the
  shader reproduces (wrap the texture coordinate, sample the lightmap
  bilinearly, colormap row `(255 - sample) >> 2`, colormap lookup).
- I did not open `R_RecursiveWorldNode` / `R_DrawWorld` in `gl_rsurf.c` /
  `gl_rmain.c`, nor the BSP29 lump specification: the PVS and BSP walk are
  not reimplemented, the GPU path calls the engine's existing `bsprender` on the
  CPU and draws the faces it returns.

## Design

- Per map, once: every drawn face is a triangle fan of vertices that carry the
  world position, the texture uv, the lightmap uv, and the face's rectangles
  in two atlases (base textures, 2048 x 320 texels for e1m1; lightmap planes,
  2048 x 207) and a 256 x 64 colormap texture, all `r8uint`.
- Per frame: `worldview.Visible` (PVS marking and BSP walk) gives the faces in
  the walk's order; one `Recorder` submit writes the 64-byte uniform (view
  transform, field of view) and issues one `DrawIndexed` per face into an
  `r8uint` target cleared to the sky-like index, with no depth test, as the
  software renderer overdraws.
- The vertex shader reproduces the software projection (view-space depth clamped
  to the near plane, perspective-correct varyings from clip `w = depth`); the
  fragment shader reproduces `FillPerspectiveLightmappedPolygon` per pixel.
- The target is an index texture the presenter can bind directly (not wired in
  this step: the check reads it back).

## Acceptance: pixel diff against the software world

`cmd/quake-worldcheck` (browser test, needs the shareware `pak0.pak` through
`QUAKE_PAK`, skipped without it): 16 fixed e1m1 views (4 in-map origins times
4 yaws, `worldview.Views`) at 320 x 200, GPU world against
`worldview.DrawSoftware`, on the Apple GPU (adapter `apple metal-3`, not a
fallback; the test fails on a fallback adapter when `QUAKE_REQUIRE_GPU=1`).

| | |
|---|---|
| Faces on the GPU | 5149 (24,645 vertices, 14,347 triangles) |
| Pixels compared | 1,024,000 (16 frames) |
| **Identical palette index** | **94.9 %** (50,324 differ, 4.91 %) |
| **Unexplained** | **1.52 %** (15,522 pixels) |
| Worst view | 4.6 % unexplained (view 15); best 0 (view 5) |

*Unexplained* means: the pixel differs and the GPU's index is not the
reference's index at any of the 8 neighbouring pixels, i.e. it is not a
one-pixel shift of the same image. **Stated tolerance: 2.5 % unexplained over
the 16 views**; measured 1.52 %. Exact equality is not expected.

A planted negative proves the comparison can fail: with the GPU given a
colormap one eighth of the table too dark (every light level), 77.6 % of the
pixels are unexplained and the check fails (`TestDamagedColormapFails`).

### Where the two differ

Measured: 3.4 % of pixels differ but are a one-pixel shift of the reference
(explained), 1.5 % are not. A first attempt to match the software scanline's
coverage by moving the GPU polygons half a pixel made 49 % of the pixels
differ and was reverted: the coverage and sample positions of the two
rasterizers already agree to within a pixel.

Not measured (hypotheses, from reading the two rasterizers):

- The software filler is only approximately perspective-correct: it divides
  by depth every `PerspSubdivStep` = 8 pixels and steps linearly in between;
  the GPU interpolates exactly. On long, steeply foreshortened floors and
  walls the texel boundary moves by a texel.
- Coverage rules at polygon edges: the software includes a pixel whose
  centre is on or inside an edge by its own rounding (`ceil` / `floor` on
  x, centres on y); the GPU's top-left rule differs on exact ties.
- Lightmap bilinear weights are float32 on the GPU and float64 in the
  software filler: an occasional colormap row off by one.
- Overdraw order: both draw in the walk's order without a depth test, so a
  one-pixel difference at an edge shows a different surface there.

## Cost at 1280 x 800

The workload is e1m1 from the fixed views, in Chrome for Testing 156 (wasm,
single thread), 7 browser runs, load 6.95 to 7.95 before and after each (13
runs discarded above 8). In each run the reference and the GPU alternate
frame by frame on the 16 views, after a warm-up pass; medians of the
per-frame times, `median (min-max)` over the 7 runs.

| | per frame |
|---|---|
| Software reference (`worldview.DrawSoftware`), wall | 75.2 ms (74.7-108.9); p95 137.4 ms |
| GPU world, CPU time (PVS walk, draw list, submit) | **0.165 ms** (0.160-0.190); p95 0.220 ms |
| GPU world, wall until the GPU is idle | **1.270 ms** (1.250-1.285); p95 1.435 ms |

GPU time itself is not measured separately: the wall figure serialises the
frame (submit, then wait for `onSubmittedWorkDone`), so it is the CPU time
plus the GPU's execution and the browser's completion latency; timestamp
queries were not enabled.

Caveats, to be read with the table:

- The reference is the engine's lightmapped perspective filler with the
  PVS walk, not the engine's usual path. The engine's own world loop
  (`game.setupRenderer`) draws unlit with the identity colormap and an
  affine filler; the lightmapped filler exists in `render` but is not what
  the engine ships, so 75 ms is not "the cost of the engine's software world".
- v0.2.1 could not be compared like for like. Its benchmark loads
  `maps/start.bsp` first (so a pak with e1m1 still renders start), it cannot
  fetch a pak in the browser, and its scene is the unlit one. A native run of
  its harness on this pak (1280 x 800, `GOMAXPROCS=1`) gave a work p50 of
  9.8 ms, but the machine load was 12.9, above the rule, so the figure is not
  published as a measurement.
- No models, particles, sprites or HUD are drawn by either side.
