# Water on the GPU, 2026-11-03

Step 4c of the GPU renderer plan: the turbulent surfaces (textures whose name
starts with `*`: water, slime, lava, teleporters) are drawn on the GPU after
the sky and before the entities (`render/gpuworld/special.go`, `fsTurb`).
Method as in [2026-11-03-sky.md](2026-11-03-sky.md).

## Bibliography (what was opened)

- `reference/common/gl_warp.c`: `turbsin` and `TURBSCALE`, `AddWarpVert`
  (the warp from a 256-entry sine table indexed by `(coordinate * 2 + time *
  TURBSCALE) & 255`), `R_UpdateWarpTextures` (GLQuake renders the warp into a
  texture by subdivided quads), the vertex/fragment program version and its
  `WARPCALC` comment (the per-pixel form: `(s + sin((t * 2 + RDT) * TIMEMULT) *
  8) / 64`). `GL_CreateWarpTableTexture` (a lookup texture of the sine).
- `d_scan.c` (`D_DrawTurbulent8`) was **not** opened; the engine's comments
  cite it and I did not check them. The oracle is the engine's port:
  `render.FillTurbulentPolygon` (u' = u + turbsin[floor((v + 40 t) / 16) & 255],
  v' = v + turbsin[floor((u + 40 t) / 16) & 255], peak 8 texels, through
  colormap row 0). This is not GLQuake's warp (index `y * 2 + time * 40.7`, scale
  1/128 or 1/64): the port is a different formula, and the GPU matches the port.
- Opened earlier for the sky and relevant here: nothing else.

## Design

Same as the sky (the same vertex layout, atlas, projection, the left-edge
coverage rule, linear coordinates), with a fragment shader that adds the warp
from the engine's table, written into the shader text from
`render.TurbSinTable()` (a unit test parses it back and compares it bit for
bit) and looks the warped texel up in colormap row 0. Time is the frame
uniform's.

## Acceptance

16 fixed views of e1m1 (`worldview.SpecialViews(KindTurb, 16)`; e1m1 has 304
`*` faces), time 3.7 s, 320 x 200, Apple GPU. Region and *unexplained* as
before. **Stated tolerance, before the first measurement: 3 %.**

| | |
|---|---|
| Region pixels | 640,675 |
| Identical palette index | 99.83 % (1,097 differ) |
| **Unexplained** | **0.05 %** (300 pixels), against 3 % |

Planted negative (`TestCorruptedWaterFails`): the GPU gets water textures with
every palette index shifted by 16: 99.95 % unexplained, the check fails.

### Ablation (`TestTurbAttribution`)

| probe | region px | differ | unexplained |
|---|---|---|---|
| nothing removed | 640,675 | 0.17 % | 0.05 % |
| texture one flat colour | 640,391 | 0.17 % | 0.04 % |
| no animation (time 0) | 640,677 | 0.36 % | 0.04 % |
| both | 640,391 | 0.17 % | 0.04 % |

With a flat texture the 0.17 % that remains is coverage at polygon edges; the
warp, the table and the animation agree to within 0.01 point.

## Cost at 1280 x 800

Seven browser runs, 1-minute load 6.1 to 7.0 before and after (3 runs
discarded above 8), paths alternating frame by frame on the 16 views; medians
(min-max).

| per frame | time |
|---|---|
| Engine software frame: `worldview.DrawEngine` world + `FillTurbulentPolygon` | 11.875 ms (11.780-12.020); p95 25.2 |
| Engine water fill alone | **8.420 ms** (8.290-8.595) |
| GPU world + water, wall until idle | 1.990 ms (1.875-2.125); p95 2.41 |
| **GPU water alone** (lit faces left out of the pass; the PVS walk still runs) | **2.005 ms** (1.930-2.090) |
| GPU world alone, wall | 0.910 ms (0.875-0.950) |

Water alone: 8.42 ms on the CPU against 2.0 ms of GPU wall time, about 4.2
times. This is the heaviest part of the three: the water pass costs about 1.1
ms more than the world alone, where the sky costs nothing measurable. The
views look at water, so it fills large parts of the frame; the fragment
shader does two dynamic table reads and a dependent texture read per pixel,
and the pass is not tuned (no draw merging: one draw per face, 304 faces on
the map). GPU time itself is not measured (go-gfx/webgpu#16).

## What remains

Water is drawn as the engine does, opaque; no transparency (`r_wateralpha`),
no underwater tint, no per-face distance subdivision; merging the per-face
draws; a probe for where the 0.17 % edge difference sits.
