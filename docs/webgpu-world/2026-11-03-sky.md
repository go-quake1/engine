# Sky on the GPU, 2026-11-03

Step 4b of the GPU renderer plan: the sky faces are drawn on the GPU
(`render/gpuworld/special.go`, `special_js.go`) after the lit faces and before
the alias entities. Method as in [2026-11-02.md](2026-11-02.md) and
[2026-11-03-alias.md](2026-11-03-alias.md).

## Bibliography (what was opened)

- `reference/common/r_sky.c`: `R_InitSky` (a sky texture is 256 x 128; the
  right half is the back layer, the left half the masked front layer, index 0
  clear), `R_MakeSky` and `R_GenSkyTile` (the two layers scroll by
  `skytime * skyspeed`).
- `reference/common/d_sky.c`: `D_Sky_uv_To_st` and `D_DrawSkyScans8`: the
  software sky is a dome, its coordinates come from the view direction
  (`6 * (SKYSIZE / 2 - 1) * normalized(end)`), not from the face's texinfo.
- `reference/common/gl_warp.c`: opened for the water (next step); it holds no
  sky code (`gl_sky.c` does and was not opened).
- The oracle is the engine's port, as in the earlier steps:
  `render.FillSkyPolygon` on `bsprender.TransformFace`, which is what
  `game.setupRenderer` runs. **It is not tyrquake's dome**: it samples the
  face's texinfo coordinates, back layer at half scale, front layer at twice the
  scroll. The GPU matches the port; making the sky a dome is a separate change
  to the engine's reference, not to the GPU.

## Design

- Sky faces (texture name `sky*`) are kept apart from the lit faces
  (`worldview.World.Special`, `VisibleSpecial`), so the lit world and its
  step 3 figures are unchanged. Per map, once: a triangle fan per face (position,
  texinfo uv, the face's rectangle in a texture atlas).
- Vertex shader: the world's projection. Fragment shader: `@interpolate(linear)`
  coordinates (the port is affine in screen space), the front layer at
  `u + 16 t`, the back layer at `u / 2 + 8 t`, wrapped, index 0 of the front
  layer clear; the raw index is written (no colormap).
- The same coverage rule as the alias pass (the port takes a pixel by its left
  edge): polygon half a pixel right, fragment half a pixel further along.
- The frame uniform grew to 80 bytes: time in seconds (`Renderer.Time`).

## Acceptance

16 fixed views of e1m1 (`worldview.SpecialViews`): sky faces at an even stride,
each seen from the first of a fixed list of distances, on either side of its
plane, whose eye is in open space with a clear line to a point 4 units in front
of the face's centre, looking at the centre. Time 3.7 s. 320 x 200, Apple GPU.
Region and *unexplained* as for the alias pass. **Stated tolerance, before the
first measurement: 3 %.**

| | |
|---|---|
| Region pixels | 685,460 (16 views; e1m1 has 63 sky faces) |
| Identical palette index | 95.57 % |
| **Unexplained** | **2.32 %** (15,900 pixels), under the 3 % tolerance |

Planted negative (`TestCorruptedSkyFails`): the GPU gets a sky texture with
every palette index shifted by 16: 99.84 % unexplained, the check fails.

### Ablation (`TestSkyAttribution`)

| probe | region px | differ | unexplained |
|---|---|---|---|
| nothing removed | 685,460 | 4.43 % | 2.32 % |
| sky texture one flat colour | 684,945 | 0.07 % | 0.02 % |
| no scroll (time 0) | 685,460 | 4.32 % | 1.53 % |
| both | 684,945 | 0.07 % | 0.02 % |

Coverage agrees (flat texture: 0.02 %); what differs is the texel a pixel takes.
That is **not isolated**. Candidates: sky faces are the largest polygons on the
map and partly off screen, where the GPU's fixed-point vertex snapping and
float32 interpolation of coordinates in the thousands move a coordinate by a
fraction of a texel; the scroll adds to it (1.53 % without). I did not run a
probe that separates them.

## Cost at 1280 x 800

Seven browser runs, 1-minute load 6.9 to 7.5 before and after (1 run
discarded above 8), the paths alternating frame by frame on the 16 views;
medians (min-max).

| per frame | time |
|---|---|
| Engine software frame: `worldview.DrawEngine` world + `FillSkyPolygon` | 8.575 ms (8.525-8.810); p95 14.0 |
| Engine sky fill alone | **6.115 ms** (5.990-6.205) |
| GPU world + sky, wall until idle | 0.590 ms (0.550-0.670); p95 0.875 |
| **GPU sky alone** (lit faces left out of the pass; the PVS walk still runs) | **0.585 ms** (0.545-0.665) |
| GPU world alone, wall | 0.785 ms (0.750-0.835) |

The sky alone is 6.1 ms on the CPU and 0.585 ms of GPU wall time, about 10
times, with the wall-time floor of about half a millisecond noted in the alias
document (so the ratio is a lower bound). The views are chosen to look at sky,
so they are sky-heavy: this is the sky's worst case, not a typical frame.
GPU time itself is not measured (go-gfx/webgpu#16).

## Update: the reference is now Quake's dome (step 5)

Step 4 compared the GPU with `render.FillSkyPolygon`, a texinfo-based
simplification, and said so. I have now ported the original from
`reference/common/r_sky.c` (`R_InitSky`, `R_MakeSky`, `R_SetSkyFrame`) and
`d_sky.c` (`D_Sky_uv_To_st`, `D_DrawSkyScans8`), with `SKYSIZE`, `SKYMASK`,
`R_SKY_SMASK` and `R_SKY_TMASK` (`d_iface.h`, `d_local.h`):

- the coordinates of a pixel come from its **view direction**, not from the
  face: `end = 4096 vpn + wu vright + wv vup` with `wu = 8192 (u - width/2) /
  max(width, height)`, `end.z *= 3`, normalised, then `s = (skytime * 8 + 378
  end.x) * 65536` and `t` likewise from `end.y` (6 * (SKYSIZE / 2 - 1) = 378);
- the texture is composed by `R_MakeSky` into a 128 x 128 table: the masked
  left half scrolled by `(int)(skytime * 8)` in both directions where it is
  not clear, the solid right half, which does not move, elsewhere;
- `skytime` is `cl.time` modulo 512 (`R_SetSkyFrame`: gcd(8, 2) = 2, so
  128 * 4 * 1);
- the spans are 32 pixels, `s` and `t` exact at their ends and stepped
  linearly (a shift by 5, a division for the last).

`render.QuakeSky`, `SkyST`, `SkySpan` and `FillSkyQuake` port that; the
engine's game and runner draw the sky with them (a texture that is not 256 x
128 keeps the old fill). Pinned tests (`render/sky_quake_test.go`):
`SkyFrameTime` at 0, 511.5, 512, 600, 1024.25; `SkyST` at the screen centre
(`378 * 65536` and `0`; `458 * 65536` and `80 * 65536` at skytime 10) and one
pixel to the right; `R_MakeSky`'s shift on a one-pixel layer; the exact
sub-span starts. What stays the engine's own is which pixels a polygon
covers.

The GPU shader computes the same direction per fragment and composes the two
halves in the shader (no table upload); it does not reproduce the 32-pixel
sub-spans. Same 16 views, same 3 % tolerance:

| | region px | differ | unexplained |
|---|---|---|---|
| step 4 (port reference) | 685,460 | 4.43 % | 2.32 % |
| **Quake reference** | 685,460 | 4.90 % | **0.30 %** |
| texture one flat colour | 684,945 | 0.07 % | 0.02 % |
| no scroll | 685,460 | 5.41 % | 0.31 % |

The planted negative still fails (99.83 %). The 2.32 % of step 4 is gone:
it was the GPU being compared with a sky that was not the one it had been
written to match; the unexplained pixels are now 0.30 %, and the differing
ones (4.9 %) are the 32-pixel steps, which are linear where the shader is
exact.

Interleaved, 1280 x 800, 7 rounds, load 4.7 to 5.1 (not comparable with
step 4's 6.9 to 7.5): engine software frame with sky 5.24 ms (4.94-5.26);
Quake sky fill alone 2.53 ms (2.35-2.55); GPU world + sky 0.44 ms; GPU sky
alone 0.415 ms (0.395-0.44); GPU world alone 0.71 ms.
