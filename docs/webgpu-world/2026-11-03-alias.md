# Alias models on the GPU, 2026-11-03

Step 4a of the GPU renderer plan: monsters, items and the view weapon are
drawn on the GPU (`render/gpuworld`, `alias.go`, `alias_js.go`), over the world,
into the same 8-bit index frame. Method as in [2026-11-02.md](2026-11-02.md):
pixel diff against the engine's own software path on fixed views, a stated
tolerance, an ablation, a planted negative, then interleaved timings.

## Bibliography (what was opened)

- `reference/common/r_alias.c`: `R_AliasSetUpTransform` (line 408: columns
  forward, minus right, up; pitch reversed), `R_AliasTransformFinalVert` and
  `R_AliasTransformAndProjectFinalVerts` (per-vertex light:
  `r_ambientlight` plus `r_shadelight * lightcos` for negative cosines),
  `R_AliasSetupLighting` (line 672: ambient clamps, the light vector
  `{0, 0, -1}`), the `ALIAS_Z_CLIP_PLANE` tests.
- `reference/common/include/modelgen.h`: `mdl_t`, `stvert_t`, `dtriangle_t`
  (`facesfront`), `trivertx_t` (3 bytes and a light normal index),
  `ALIAS_ONSEAM`.
- `reference/common/gl_mesh.c`: the back-face seam rule (lines 97 and 118:
  `!tri->facesfront && stvert->onseam` shifts `s` by half the skin width).
- `d_polyse.c` and `gl_rmain.c` were not needed: `gl_rmain.c` has no alias
  drawing in this tree (`R_DrawAliasModel` is not there; grep finds none).
- The engine's own port is the oracle, as in step 3: `render.DrawAliasInterpLit`
  (the call `game.setupRenderer` makes, shade 0.3 ambient + 0.7 from straight
  down). It differs from tyrquake's software renderer: light is the mean of a
  triangle's three vertex lights (flat per triangle, not Gouraud), and the
  texture is affine in screen space. The GPU matches the port, not tyrquake.

## Design

- Per set of models, once: every frame's pose as one `uint32` per vertex
  (x, y, z bytes and the light byte computed with
  `render.ComputeAliasVertexLights`, the reference's function, since the
  engine's light direction is fixed in the world), the triangle corners
  (vertex index, s with the seam shift already applied, t), a skin atlas.
- Per frame: one 112-byte record per entity (rotation rows from
  `render.EntityRotation` plus origin, model scale and origin, the two pose
  bases, the lerp, the skin rectangle) and one non-indexed draw per entity.
- Vertex shader: byte-space lerp rounded as `lerpAliasPose` does, decode,
  rotate, translate, view, project; the triangle is dropped (collapsed) when a
  vertex is nearer than 8 or the screen winding is back-facing; the row is
  `(255 - mean light) * 64 / 256`.
- Fragment shader: skin coordinates interpolated with `@interpolate(linear)`,
  floor, wrap, colormap lookup. No depth test; entities are drawn after the
  world in list order, as the engine does.
- One quirk of the reference had to be reproduced. `render.FillTexturedPolygon`
  takes a pixel when its left edge, not its centre, is inside the span, and
  samples at the centre. The GPU polygon is moved half a pixel right and the
  fragment samples `dpdxFine` half a pixel further. First measurement without
  it: 7.27 % unexplained (above the 3 % stated beforehand); with it 0.10 %.
  The cause was found by the ablation below (flat skin dropped the figure to
  1.1 %, so it was texel selection at edges), then confirmed by the fix.

## Acceptance

Sixteen fixed views of e1m1 (`worldview.AliasViews`): 10 monsters and 6 items
(armor, weapons, artifacts) taken at an even stride from the entity list, each
seen from the first of a fixed list of distances and bearings whose eye is in
open space with a clear line to the entity; each view carries the entities
with a clear line to its eye within 1500 units and the view weapon (the shotgun
at the eye; the engine does not draw a view weapon in software yet, both sides
here do). Every third monster is caught between frames 1 and 2 at lerp 0.5.
320 x 200, Apple GPU (`apple metal-3`, not a fallback).

The region compared is the **alias region**: the pixels where either side's
frame with the entities differs from the same side's frame without them.
*Unexplained* is as in step 3 (differs, and no 8-neighbour of the reference
has the GPU's index). **Stated tolerance, before the first measurement: 3 %
unexplained over the region.**

| | |
|---|---|
| Region pixels compared | 50,250 (16 views) |
| Identical palette index | 99.80 % (101 differ) |
| **Unexplained** | **0.10 %** (49 pixels), against the 3 % tolerance |

Planted negative (`TestCorruptedSkinFails`): the GPU is given skins with
every palette index shifted by 16, the reference keeps the true ones: 97.35 %
unexplained, the check fails.

## Cost at 1280 x 800

Seven browser runs (Chrome for Testing 156, wasm, single thread, Apple GPU),
1-minute load 6.4 to 7.7 before and after each (5 runs discarded above 8).
In each run the paths alternate frame by frame on the 16 alias views after a
warm-up pass; medians (min-max) over the runs. Each frame has the entities
a server would send (see above).

| per frame | time |
|---|---|
| Engine software frame: `worldview.DrawEngine` world + the engine's alias pass (`DrawAliasInterpLit`) | **14.90 ms** (14.32-15.05); p95 21.4 |
| Engine software alias pass alone | 0.595 ms (0.565-0.605) |
| GPU world + alias, wall until the GPU is idle | **0.755 ms** (0.720-0.775); p95 1.0 |
| GPU alias alone (lit faces left out of the pass; the PVS walk still runs), wall | 0.635 ms (0.555-0.670) |
| GPU world alone, wall | 1.120 ms (1.045-1.155) |

Comparable and not: the whole-frame pair is 14.90 ms against 0.755 ms, with
the step 3 caveat (the GPU draws the lit, perspective-correct world, the
engine's path an unlit affine one). **The alias pass on its own is not faster
on the GPU**: 0.635 ms of wall time against 0.595 ms of CPU time; the GPU wall
figure has a floor of about half a millisecond (submit, completion latency),
and the 16 views hold few, small models. The "world alone" figure being larger
than "world + alias" shows the order effect of the interleaving (it runs right
after the CPU frames) and that differences below about 0.3 ms are not
resolved by wall time; GPU timestamps (go-gfx/webgpu#16) are still needed to
separate GPU time. The view weapon is drawn by both sides here but not by
the engine's software path today.

## What remains

Frame groups use their first sub-frame (no cycling of torches and flames);
alias entities are not frustum-culled (the near-clip and winding tests drop
what they should, the rest is rasterised and clipped); brush entities
(health and ammo boxes, doors) are not drawn; the colormap row is the
engine's per-triangle mean, not tyrquake's per-vertex Gouraud light.
