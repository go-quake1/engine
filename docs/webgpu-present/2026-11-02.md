# WebGPU presenter, 2026-11-02

Step 2 of the GPU renderer plan: the software rasterizer still draws the
8-bit frame, but the palette lookup and the scaling to the canvas move to a
fragment shader (`render/webgpupresent`, go-gfx/webgpu v0.3.0), with one
`Recorder` submit per frame. This compares it with the software path of
the standalone page, in the same harness as the
[baseline](../baseline/2026-11-02.md).

## Setup

| | |
|---|---|
| Harness | `cmd/quake-bench present`, built from engine commit `ca74511294da6cd6878ec81a372ed1de20a3be23` (branch `feat/webgpu-present`, #50) |
| Machine | Apple M4 Max, 16 cores, macOS 27.2 |
| Go | go1.27.3, GOOS=js GOARCH=wasm |
| Browser | Chrome for Testing 156 (`HeadlessChrome/156.0.0.0`, Playwright chromium-1248), full browser in headless mode |
| GPU | **real**: adapter `apple metal-3`, `fallback false` (a webgpu round fails on a fallback adapter; SwiftShader never counts as a GPU) |
| Assets | procedural scene (stub host + synthbsp, `pak: procedural`), as the baseline: no shareware `pak0.pak` on this machine |
| Workload | demo-orbit camera, fixed 1/60 s step, 500 (320x200) or 200 (1280x800) warm-up frames, then 5000 or 2000 measured frames per round |
| Rounds | 7 per configuration, interleaved A B C A B C ... |
| Load | 1-minute load read before and after every round; a round above 8 is discarded and redone. Accepted rounds: 6.55 to 7.41 (320x200), 4.16 to 6.40 (1280x800). The 320x200 run discarded 24 attempts while another process pushed the load to 73, then continued. |

Configurations:

- **wasm**: the baseline: the frame is discarded (null display), browser
  without GPU (`--disable-gpu`), as in the baseline run.
- **wasm+canvas2d-present**: what the standalone page did before: RGBA
  expansion on the CPU, `CopyBytesToJS`, `putImageData`.
- **wasm+webgpu-present**: the 8-bit frame uploaded as an `r8uint`
  texture (the palette, 256x1, only when it changes), palette lookup and
  scaling in a fragment shader, one `Recorder` submit.

The two presenting configurations run in the same GPU-enabled browser, so
only the display path differs. Cells are `median (min-max)` over 7 rounds.
Frame work is Begin-to-End on the CPU (what the main thread spends); the
GPU runs asynchronously, so the **wall** row adds the wait for the GPU to
finish every frame (`onSubmittedWorkDone`) over the measured frames: it is
the end-to-end cost.

The software figures agree with the baseline (1280x800 p50 3.475 ms,
320x200 p50 0.225 ms there), so the rounds are comparable. At 1280x800 the
GPU presenter is 2.4x faster than the software page path at the median
(1.415 vs 3.470 ms) and 2.0x on the wall time; at 320x200 it is 1.7x
faster at the median (0.135 vs 0.225 ms) and 1.3x on the wall time. The
gain is the CPU expansion plus `putImageData` that no longer exist.

## Correctness

`cmd/quake-presentcheck` reads the canvas back (ImageBitmap drawn on a 2D
canvas) and compares every pixel of six frames (scale 1 and 3, a padded
pitch, a palette change between frames) with `webgpupresent.Reference`:
all 76800 pixels equal on the Apple GPU. A planted wrong palette index (the
GPU is fed one changed index, the reference keeps the true one) fails it,
naming pixel (7,5). The macOS CI lane requires a non-fallback adapter; the
Linux lane runs the same check on SwiftShader (correctness only).

## Open defects and caveats

- **Allocations.** The presenting path allocates 42 to 43 objects and
  2568 bytes per frame against 10 and 584 for the software path (the
  `syscall/js` calls and the recorded pass). Allocation counts are exact:
  this is a defect to remove (reuse the pass descriptor, the view and the
  bind-group call arguments), not noise.
- **What is measured.** The scene is the procedural fallback, not a Quake
  level, and the page is headless: the frames are presented to an
  offscreen canvas without being composited to a screen. Frame work does
  not contain the GPU's time; the wall row does.
- **Scaling.** `Reference` is exact for scale 1 and integer upscales; the
  shader picks the texel under the pixel centre, so other ratios may
  differ on an exact boundary. The page picks the largest integer scale
  that fits the canvas.
- **Timer.** About 5 microsecond resolution with COOP/COEP: 320x200
  percentiles are quantised.
- **Recorder v0.3.0** has no texture write: the index frame and the
  palette use `Queue.WriteTexture` (one JS call each) next to the single
  Recorder submit.

## What remains for BSP-on-GPU

The BSP walk and PVS, the surface cache and lightmaps, the span rasterizer
(`FillTexturedPolygon`), alias models, particles, sprites, sky and the 2D
layers are all still software. Next: upload the world's vertex data and
textures once, draw faces from the PVS list with the lightmap atlas in a
fragment shader, then models and particles, keeping this presenter as the
fallback for an adapter-less browser.

## Reproduce

```sh
GOOS=js GOARCH=wasm go build -o bench.wasm ./cmd/quake-bench
go run ./cmd/quake-bench present --rounds 7 --frames 5000 --warmup 500 \
    --wasm bench.wasm --chromium <Chrome for Testing> --profile <durable dir>
go run ./cmd/quake-bench present --rounds 7 --frames 2000 --warmup 200 \
    --width 1280 --height 800 --wasm bench.wasm --chromium ... --profile ...
QUAKE_CHROMIUM=<chromium> QUAKE_PROFILE=<dir> QUAKE_REQUIRE_GPU=1 \
    go test ./cmd/quake-presentcheck
```
