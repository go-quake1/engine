# WebGPU presenter, batched texture writes, 2026-11-02

Follow-up to [2026-11-02.md](2026-11-02.md). That run left two defects: the
presenter made two direct texture-write calls next to its single Recorder
submit, and it allocated 42 to 43 objects per frame against 10 for the
software path. Now:

- go-gfx/webgpu v0.4.0 adds `Recorder.WriteTexture` (a batched
  `queue.writeTexture`, wire stream version 3, fuzzed; go-wasmcontainers/gpu
  and go-virtio/gpudev build and test against it). The presenter's frame is
  **one JS call** (`replay`), plus one `put` of the new canvas view.
- go-gfx/webgpu v0.5.0 cuts a frame of the batched path from 24 to 4
  allocations (`TestFrameAllocs`, budget enforced): `BeginRenderPass`
  no longer builds and drops the JS descriptor maps (14 allocations), the
  Recorder owns its pass recorders, `CreateView(nil)` passes no object, and
  `Surface.CurrentView` returns the same Go handles every frame.
- The presenter uses them (engine commit
  `6597ab7326dce4a754494daf15744fb16ea6322b`, go-gfx/webgpu v0.5.0).

Same machine, browser, GPU (`apple metal-3`, not fallback), harness, load
rule (rounds above 8 discarded and redone) and 7 interleaved rounds as the
first run. Accepted loads: 7.01 to 7.85 (320x200), 2.75 to 7.93 (1280x800).

## Allocations

| | software (`wasm`, `canvas2d`) | webgpu, first run | webgpu now |
|---|---|---|---|
| allocs / frame | 10 | 42 (43 at 1280x800) | **13** |
| bytes / frame | 584 | 2568 | **608** |

The 3 allocations and 24 bytes left are in `syscall/js`: the closure of the
`try` wrapper around the view call and the argument slices of the two `Call`s
(`put` of the new view, `replay`). Removing them needs a `syscall/js` call
without a closure or argument slice, which Go does not offer.

## Timings (median of the per-round p50, min-max)

| frame work p50 (ms) | wasm (baseline config) | wasm+canvas2d-present | wasm+webgpu-present |
|---|---|---|---|
| 320x200 | 0.215 (0.205-0.230) | 0.230 (0.215-0.245) | 0.135 (0.115-0.140) |
| 1280x800, run 1 | 3.265 (3.125-3.535) | 3.765 (3.350-3.960) | 1.945 (1.570-2.395) |
| 1280x800, run 2 | 3.305 (3.220-3.530) | 3.865 (3.415-4.095) | 1.605 (1.565-2.495) |

Wall time per frame to GPU idle: 320x200 0.233 / 0.255 / 0.180 ms; 1280x800
run 1 3.456 / 4.335 / 2.152 ms, run 2 3.480 / 4.205 / 2.112 ms.

Against the first run (1280x800 webgpu p50 1.415 ms, 320x200 0.135 ms):

- At 320x200 nothing changed (0.135 ms).
- **At 1280x800 the median is not better, and probably worse**: 1.605 to
  1.945 ms against 1.415 ms, with a wider spread (the machine was also
  slower for the software configurations: canvas2d 3.77 to 3.87 ms against
  3.47 ms). The presenter is still 1.9 to 2.4 times faster than canvas2d at
  the median, against 2.5 times before. This is an open defect, not noise to
  explain away: a hypothesis, not measured, is the extra 1 MB copy per frame
  that batching adds (the Recorder copies the frame into its data stream,
  `replay` copies it to JS, and `writeTexture` reads a subarray of it, where
  the direct call loaded the staging array once). Fix to try: let the
  Recorder write the caller's bytes straight to the JS staging array.
- The gain of this step is the allocation count (42 to 13) and the single JS
  call, not the CPU time at 1280x800.

## Reproduce

As in 2026-11-02.md, with the `present` subcommand; the allocation budget:
`GOOS=js GOARCH=wasm go test -run TestFrameAllocs -exec=<wasmbrowser>` in
go-gfx/webgpu.
